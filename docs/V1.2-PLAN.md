# 1.2 plan: more frameworks, and real SSR

Two independent goals. SSR is a bug fix with a documented promise behind it;
the new adapters are additive. They ship together because the SSR work changes
what an adapter has to do, and doing it after four more adapters exist means
fixing it five more times.

## The SSR problem, stated precisely

`packages/vanilla/src/picker.ts` opens with:

```ts
export class OklchPickerElement extends HTMLElement {
```

That expression evaluates at import time, so the module cannot be loaded where
there is no DOM. Importing `oklch-picker` or `oklch-picker/register` in Node
throws `HTMLElement is not defined` before any code runs.

**Who this actually breaks.** Not Rails, Laravel, Django or PHP: those serve
the tag as text and never import the module server-side. It breaks JavaScript
SSR, which is Astro, Next, Nuxt, SvelteKit, Remix. The README recommends the
element for "any server-rendered page", which is true for the template
languages and false for the JS ones.

**Why nothing has caught it.** The docs site and the Astro example both import
inside a `<script>` block, which Astro bundles for the client only. They work by
convention rather than by design. Moving that import into a component's
frontmatter crashes the build.

The core is already DOM-free and imports cleanly in Node, which is the hard half
and was done from the start.

## Phases

Each phase leaves the repo green and is worth its own commit.

### 1. Make the vanilla element import-safe

Guard the class definition so the module loads anywhere, and make `register()` a
no-op without `customElements`. The element is inert on a server, which is
correct: there is nothing to upgrade.

```ts
const Base = typeof HTMLElement === "undefined"
  ? (class {} as typeof HTMLElement)
  : HTMLElement;
```

The cast is the honest shape of this. A server-side `OklchPickerElement` is a
class nobody can construct, and pretending otherwise in the types would be
worse than one contained assertion.

**Done when** `node -e 'import("oklch-picker/register")'` exits cleanly.

### 2. Prove SSR per adapter, in CI

Add `react-dom/server`, `vue/server-renderer`, `svelte/server` and Solid's
`renderToString` as dev dependencies, then a `test/ssr.test.ts` that renders
each adapter with no DOM globals and asserts real markup comes back: three
sliders, the chart path, the value in the field.

This is the phase that makes SSR a promise rather than a hope. Without it the
next refactor silently reintroduces a `document` reference and nobody knows
until an issue arrives.

**Done when** the suite fails if any adapter touches the DOM at module scope or
during first render.

### 3. Hydration

Server markup has to match what the client renders first, or frameworks warn
and discard it. The risks are known:

- `Math.random()` in any id. `GamutChart` takes an `id` prop already, and the
  site's `Picker.astro` generates one per instance; both need checking for
  stability across the two renders.
- The gradient `id` in the chart SVG shares a document-wide namespace.
- `resolveCurrent` reads a draft that only exists on the client. It should
  resolve to the stored value on the server, which it already does with a null
  draft, but that wants a test rather than an assumption.

**Done when** rendering server-side and hydrating produces no warning in React
and Vue, asserted in the test rather than eyeballed.

### 4. Document what each stack needs

One page on the site, one section in the README. Astro, Next, Nuxt, SvelteKit,
and the template languages that were never affected. The current wording claims
more than the code delivers, so this phase is a correction as much as an
addition.

### 5. Angular

The largest piece. A standalone component over `pickerModel`, with
`ChangeDetectionStrategy.OnPush` and signals rather than zone-based change
detection.

Open questions to settle before writing it:

- **Build.** `ng-packagr` is the convention but adds a heavy toolchain to a repo
  that builds everything with tsdown in under a second. A plain ESM build with
  `@angular/core` as a peer dependency may be enough for a component this
  simple. Worth trying the cheap path first.
- **Version floor.** Signals need 16+, standalone components 14+. Targeting 17+
  keeps the adapter small; anything lower means supporting NgModules too.
- **Testing.** The existing five share one vitest setup. Angular's TestBed does
  not fit that, so this may need its own project in `vitest.config.ts`.

### 6. Lit **(done: no package)**

Prototyped, and the prototype answered the question. A real Lit component
against the bare element needed no adapter at all: `.gamut=${P3}` and
`.presets=${[...]}` bind natively, because Lit's `.` syntax is exactly the
property-binding escape hatch a wrapper would have provided. Events reach Lit
state, and both entry points already type the tag, so `picker.value` is a string
and `event.detail.colour` resolves.

Shipped as a documented recipe alongside Alpine and HTMX instead, on
`/docs/recipes`. The prototype did turn up one thing worth writing down: a
native class field overwrites the accessor Lit installs, so reactive state has
to be assigned in the constructor or updates stop firing.

### 7. Qwik

Resumability makes this the least like the others. Qwik serialises state rather
than re-running components, so the draft, the pointer handlers and the chart's
memo all need `$()` boundaries and cannot close over live objects the way the
React adapter does.

The headless model suits this well: `pickerModel` is a pure function of the
current colour, which is exactly what a resumable component wants. But the
adapter will not look like a translation of any existing one, and estimating it
from the others would be wrong.

### 8. Alpine and HTMX **(done)**

No package, as expected. Both already work with `<oklch-picker>`, so what was
missing was a recipe, now on `/docs/recipes` with Lit.

One correction to the plan's own wording: `x-model` is the wrong binding.
Alpine's `x-model` recognises built-in form controls, so on a custom element it
sets the initial value and then never updates, which looks right until the first
drag. `x-effect="$el.value = colour"` with a `change` handler is what works, and
that was verified against the real element rather than reasoned about.

## Deliberately deferred

- **Frameworks beyond these.** Preact already works through the React adapter.
  Aurelia and Marko are both smaller than Qwik, which is itself the smallest
  ecosystem shipped here.

  **Ember was prototyped and rejected**, which is worth recording so it is not
  reopened on download counts alone. It renders: a Glimmer component compiles,
  args arrive, click handlers fire. Three things stopped it. `@ember/*` and
  `@glimmer/*` are virtual modules that exist only inside an Ember build, so
  every import needed a hand-written alias block that is a fiction rather than
  how Ember resolves them. `@tracked` is decorator syntax with no working
  non-decorator path found, so reactivity, the whole point of the adapter, was
  never proven: the probe rendered 10 and stayed 10 after a click. And it pulls
  268 packages against Qwik's 4.

  Underneath all three: Ember expects to own the build. Every other adapter
  ships source or a small bundle and slots into the consumer's toolchain, while
  an Ember addon is built by `ember-cli` with its own resolver. Doing it
  properly means bringing that into the monorepo, which is a larger job than any
  adapter so far and should be a deliberate choice rather than a side effect.

  **Stencil** belongs with Lit: it compiles *to* custom elements, so a Stencil
  app can use `<oklch-picker>` today. A recipe, not a package.
- **A shared adapter test suite.** Seven adapters testing the same behaviour
  seven times is the obvious next refactor, but doing it before the new ones
  exist means designing for adapters that have not been written.

## Risks

- **Seven adapters is a lot of surface.** Every behaviour change already means
  five edits; this makes it eight. The core carries the behaviour, which is what
  makes that survivable, and the rule that logic belongs in `model.ts` becomes
  more important rather than less.
- **Angular's toolchain** is the most likely thing to slow this down, and it is
  worth timeboxing the cheap build before reaching for `ng-packagr`.
- **Claiming SSR is a promise.** Once documented, it needs the tests from phase
  2 to stay true. Without them this regresses within two releases.
